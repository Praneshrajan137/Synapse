# Runbook — Materialize Feast into the running path (demand_prophet)

**Goal:** make `FeatureProvider.get(...)` return `source=FEAST` (not `FALLBACK`) for
the demand_prophet serving path. **Related:** [ADR-043](../adr/ADR-043-agent-reality-pattern.md),
[ADR-041]. **Invariants:** per-city Redis DB index (E-S6-03), Mumbai `monsoon_intensity`
(E-S6-09). **Cost:** $0 — Redis is already in the compose stack.

## Why this is needed

`scripts/build_feature_store.py` writes the offline parquet, but `feast apply` +
`feast materialize` to the Redis online store is an operator step. Until it runs,
the online store is empty, every fetch degrades, and demand_prophet serves the
honest fallback. The pipeline's `FEATURE_REFS` are pinned to the registered
`sku_demand_signals` FeatureView by `packages/tests/test_feast_ref_consistency.py`
(a ref mismatch would make this materialization useless — that test fails CI first).

## Prerequisites

- Redis up (the compose `redis` service; Bengaluru uses db index 0, E-S6-03).
- `feast` installed in the environment.
- `data/bengaluru/demand_history.csv` present (generated by the data-gen step).

## Steps (Bengaluru)

```bash
# 1. Build the offline feature parquet in the exact sku_demand_signals schema.
python scripts/build_feature_store.py --city bengaluru

# 2. Register the feature views to the registry (writes data/registry.db).
cd data_fabric/feast && feast apply && cd -

# 3. Push the offline features into the Redis online store.
#    `materialize-incremental` is idempotent; use a window that covers the parquet.
cd data_fabric/feast && feast materialize-incremental "$(date -u +%Y-%m-%dT%H:%M:%S)" && cd -
```

`scripts/build_feature_store.py --city bengaluru --apply` performs steps 1–2 in one
shot (step 2 is best-effort and skips cleanly if the feast CLI is unavailable).

## Verify

```bash
# Ref consistency (no infra needed — runs wherever feast is installed):
python -m pytest packages/tests/test_feast_ref_consistency.py -q

# End-to-end (Redis up + materialized): a fetch must report FEAST, not FALLBACK.
python - <<'PY'
from feast import FeatureStore
from synapse_common.features import FeatureProvider
from agents.demand_prophet.inference.pipeline import FEATURE_REFS
store = FeatureStore(repo_path="data_fabric/feast")
res = FeatureProvider(store).get(["SKU0001"], FEATURE_REFS, store_id="STORE001")
print("source =", res.source, "degraded =", res.degraded)
assert res.source.name == "FEAST" and not res.degraded, "still degraded — check apply/materialize"
print("OK: real features flowing")
PY
```

With the serving container, confirm `GET /health` → `feast_connected=true` and a
`POST /predict` response whose provenance shows `feature_source=FEAST`,
`degraded=false` (this is what the C42 runtime gate asserts in CI).

## Mumbai (multi-city)

Use the Mumbai overlay and db index 1 (E-S6-03); the Mumbai feature views MUST carry
`monsoon_intensity` (E-S6-09) — the FeatureProvider raises and degrades if it is
missing, so a Mumbai materialize that omits it is caught immediately.

```bash
python scripts/build_feature_store.py --city mumbai --apply
cd data_fabric/feast/mumbai && feast materialize-incremental "$(date -u +%Y-%m-%dT%H:%M:%S)" && cd -
```
